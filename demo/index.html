Every component below is the real thing, wired to its real bindings. Nothing here is a screenshot or a static mock — the editor tracks your selection, the grid navigates by keyboard, and the menu returns focus to whatever opened it. Switch the theme or flip to RTL at any time; every component follows without a single direction-specific rule.

Buttons

Variants and sizes are separate classes, so they compose freely. Every state is styled: hover, active, focus-visible, disabled, and busy.

html 
<!-- Variant and size are separate classes, so they compose. -->
<button class="fc-btn fc-btn--primary">Save</button>
<button class="fc-btn fc-btn--primary fc-btn--sm">Save</button>

<!-- `disabled` leaves the tab order. `aria-disabled` stays reachable, so a
     keyboard user can find it and learn *why* it is unavailable. -->
<button class="fc-btn fc-btn--secondary" disabled>Disabled</button>
<button class="fc-btn fc-btn--secondary" aria-disabled="true">aria-disabled</button>

<!-- Busy keeps the label in the DOM. Swapping it for a spinner would leave
     the control momentarily unlabelled to a screen reader. -->
<button class="fc-btn fc-btn--primary" aria-busy="true">
  <span class="fc-btn__spinner" aria-hidden="true"></span>
  <span>Saving…</span>
</button>

<!-- Icon-only needs an explicit name: the glyph is decorative. -->
<button class="fc-btn fc-btn--ghost fc-btn--icon" aria-label="Refresh">&#8635;</button>

Rich text editor

Select some text and watch the toolbar report the marks across the whole selection. A partly-bold selection reads as not-bold, because a toolbar that lies about a partial selection is worse than one that admits it.

Type here, then select a few words.

The toolbar above updates as the selection changes — that is the onSelectionChange callback, wired in demo/demo.js.

Ready. The bindings are plain TypeScript — no build step, no bundler, no WASM.

js 
import { FutureCssEditor } from "future-css/editor";

const editor = new FutureCssEditor({
  root: "#editor-root",

  onChange: (html) => console.log(html),

  // Fires on every selection change. The payload is the state of each mark
  // across the *whole* selection, so a partly-bold range reports not-bold --
  // a toolbar that lies about a partial selection is worse than one that
  // admits it. The binding keeps its own toolbar in sync from this; there is
  // no public syncToolbar to call.
  onSelectionChange: (active) => {
    const marks = Object.entries(active).filter(([, on]) => on).map(([n]) => n);
    console.log(marks);
  },
});

// Marks are applied by calling the method, not by a callback. The toolbar
// buttons in the markup carry data-fc-mark and the binding reads them.
editor.applyMark("bold");
html 
<div class="fc-editor">
  <div class="fc-toolbar" role="toolbar" aria-label="Formatting">
    <!-- The glyph is decorative; the name is real text. -->
    <button class="fc-toolbar__item" data-fc-mark="bold" aria-pressed="false">
      <span aria-hidden="true"><strong>B</strong></span>
      <span class="fc-u-visually-hidden">Bold</span>
    </button>
  </div>

  <!-- role="textbox" + aria-multiline: contenteditable alone is not reliably
       announced as editable, and Enter needs the multiline flag. -->
  <div class="fc-editor__content fc-prose"
       contenteditable="true" role="textbox" aria-multiline="true"
       aria-label="Document body"></div>
</div>

Data grid

Click a cell, then use the arrow keys. There is exactly one tab stop: arrows move within the grid, Tab leaves it. A grid where every cell is focusable needs nine presses of Tab to escape a 3×3 and is unusable at 10,000 cells.

js 
import { FutureCssMenu } from "future-css/menu";

const menu = new FutureCssMenu({
  root:   document.querySelector("#demo-menu"),
  trigger: document.querySelector("#menu-trigger"),
  target: document.querySelector("#menu-surface"),   // right-click surface

  // Focus returns to whatever opened the menu -- every time, Escape included.
  // Losing focus to the body strands a keyboard user at the top of the page.
  onClose: (reason) => trigger.focus(),

  onAction: (action) => console.log(action),
});

Chat surface

Messages carry their state in data-fc-* attributes, so a machine reading the DOM gets role, sequence, timestamp, and lifecycle state without parsing a word of prose. The attributes are additive: styling never depends on them, and a consumer can ignore them entirely.

You 09:12

Which services are degraded right now?

Assistant 09:12

One: api in us-east-1, p95 at 187 ms.

Assistant 09:12

Full response: 14 log lines, 3 tool…

System 09:13

Metrics fetch failed — retrying in 30 s.

Assistant 09:13

Checking the worker queue…

html 
<!-- role="log" so AT announces new turns without interrupting. -->
<div class="fc-chat" role="log" aria-label="Conversation" tabindex="0">
  <!-- State is data, not class. An agent reads these; CSS reads the same
       attributes. Never derive appearance from a class that can drift. -->
  <div class="fc-msg"
       data-fc-kind="message" data-fc-id="m-2" data-fc-seq="2"
       data-fc-role="assistant" data-fc-state="complete"
       data-fc-ts="2026-10-04T09:12:04Z">
    <div class="fc-msg__meta">
      <span class="fc-msg__author">Assistant</span>
      <!-- <time datetime> carries the machine-readable value; the text is
           the human one. -->
      <time class="fc-msg__time" datetime="2026-10-04T09:12:04Z">09:12</time>
    </div>
    <div class="fc-msg__body fc-prose"><p>One: <strong>api</strong>.</p></div>
  </div>

  <!-- Truncation is ALWAYS declared, and the full value stays reachable. -->
  <div class="fc-msg" data-fc-truncated="true" data-fc-state="complete">
    <div class="fc-msg__body fc-prose"
         title="Full response: 14 log lines, 3 tool calls, 1 error.">
      <p>Full response: 14 log lines, 3 tool&hellip;</p>
    </div>
  </div>

  <!-- An error keeps its text. Styling says it failed; deleting the content
       would destroy the only record of what went wrong. -->
  <div class="fc-msg" data-fc-state="error">
    <div class="fc-msg__body fc-prose">
      <p>Metrics fetch failed &mdash; retrying in 30&nbsp;s.</p>
    </div>
  </div>
</div>

Embedded browser chrome

The browsing is an <iframe>; the design system owns the accessible, themeable chrome around it. Note the sandbox: the frame loads without allow-same-origin, so the embedded page cannot reach this origin's cookies or storage.

⚠ Not secure

Unsafe schemes are refused: try javascript:alert(1) in the address bar.

js 
import { FutureCssWebview } from "future-css/webview";
import { isSafeUrl } from "future-css/urls";

const webview = new FutureCssWebview({
  root: "#webview-root",

  // The binding already refuses javascript:, data:, and file: before they
  // reach the frame. `isSafeUrl` is exported so a consumer can apply the same
  // rule to its own links -- it is the same check, not a re-implementation.
  onNavigate: (url) => { void isSafeUrl(url); },
  onStateChange: (state) => { badge.dataset.fcState = state; },
});

webview.navigate("/demo/page.html");
webview.back();

  import { renderHighlighted } from "future-css/highlight";

  const block = document.querySelector(".fc-code");
  const lang  = block.dataset.fcLang;          // single source of truth

  block.querySelector(".fc-code__source")

Git surface

A working tree rendered from fixture data. Nothing here shells out to git or parses porcelain output — the surface is a view over status entries the application already has. Watch the order: conflicts first, then files changed in both the index and the worktree, because those are the ones where staging is a real decision.

js 
import { FutureCssGitSurface } from "future-css/git";

const git = new FutureCssGitSurface({
  root: "#git-root",
  branch: "feat/git-surface",

  // Plain data. The surface renders what it is given; it does not run git,
  // spawn a process, or parse porcelain output. Bring your own entries from
  // libgit2, a language binding, or a fixture.
  entries: [
    { path: "src/js/git.ts", index: "modified", worktree: "modified",
      before: "a\nb\nc\n", after: "a\nc\nd\nd\n" },
    { path: "src/js/new.ts", worktree: "untracked" },
    // No contents -> no line stat. Rendering +0 -0 would claim the file is
    // unchanged, which it is not; it was never read.
    { path: "README.md", worktree: "modified" },
  ],

  onSelect: (path) => showDiffFor(path),
  onStage: (path) => stageFile(path),
});

// The ordering that matters, and why:
//   conflicts first      they block everything else
//   changed in both      staging is a real decision here
//   then alphabetical    so the list does not reshuffle while you read it

// Counts are declared on the root, so a reader does not have to parse the
// header sentence to find them:
//   data-fc-staged data-fc-unstaged data-fc-conflicted data-fc-untracked
// and data-fc-branch-state is "unborn" rather than the header being empty.

Context strip

Provider, model, and effort, resolved as one piece of state. Change the provider and the model follows it — a model from one provider selected under another is a request nobody can fulfil. Change back and each provider restores the model it had. Switch to a model with no reasoning and effort dims and says so rather than silently ignoring the setting.

Model
Effort

js 
import { FutureCssContextStrip } from "future-css/context-strip";

const strip = new FutureCssContextStrip({
  root: "#strip-root",

  // The catalogue is the application's, not the library's. These bindings do
  // not know what any vendor sells.
  providers: [
    {
      id: "anthropic", name: "Anthropic",
      models: [
        { id: "opus-5", name: "Claude Opus 5",
          reasoning: true, parameters: { context: "200k" } },
        { id: "haiku-5", name: "Claude Haiku 5",
          parameters: { context: "200k" } },
      ],
    },
  ],

  onChange: (state) => send({ ...state }),
});

// The strip owns the relationships between the controls, which is why it is a
// component rather than three selects placed side by side:
//
//   provider -> model   the model is re-resolved when the provider changes
//   per-provider memory    switching back restores that provider's model
//   model -> effort      dimmed and explained when the model ignores it
//
// Whole state is mirrored to data attributes on the root, so a machine reads
// it without walking three selects and parsing their labels:
//   data-fc-provider="anthropic" data-fc-model="opus-5" data-fc-effort="high"
// and data-fc-effort is *absent* -- not empty -- when effort does not apply.
// The attributes are additive: the strip works for a consumer that ignores them.

Chat composer

Enter sends, Shift+Enter adds a line — and neither fires while an IME candidate is being composed, which is the bug every composer ships and nobody notices without a composing keyboard. Send and Stop are one control whose meaning changes with data-fc-state: the same element, so focus never moves mid-run. Stopping keeps your draft.

    html 
    <div class="fc-composer" data-fc-state="idle">
  <!-- A real <textarea>, not contenteditable: an IME-composed character
       fails silently in a contenteditable region. -->
  <label class="fc-u-visually-hidden" for="composer-input">Message</label>
  <textarea class="fc-composer__input" id="composer-input" rows="2"></textarea>

  <!-- A list, so AT announces how many are attached. -->
  <ul class="fc-composer__attachments" id="composer-attachments"></ul>

  <div class="fc-composer__row">
    <!-- One control, two meanings. Replacing the button would move focus. -->
    <button class="fc-btn fc-btn--primary fc-composer__send"
            id="composer-send" data-fc-state="idle" disabled>Send</button>
  </div>

  <!-- Always present and updated in place: a live region that gains content
       announces, one that gains and loses silently does not. -->
  <p class="fc-composer__status" role="status"></p>
</div>
    js 
    import { FutureCssComposer } from "future-css/composer";

const composer = new FutureCssComposer({
  root: "#composer-root",

  onSubmit: (text, attachments) => {
    // The draft is cleared only AFTER this returns. If it throws, the user's
    // text is still there -- losing it to a bug in this handler would be silent.
    stream(text, attachments);
  },

  // Aborting a run is not composing a message: the draft is deliberately kept.
  onStop: () => currentStream?.abort(),
});

composer.setRunning(true);   // Send becomes Stop; input becomes read-only
composer.addAttachments([file]);
composer.removeAttachment(0);

// The binding handles:
//   Enter               send
//   Shift+Enter         newline
//   Enter + isComposing NOT a send -- the IME case everything else misses
//   readOnly, not disabled, while running: a disabled field leaves the tab order
//   drag and drop, paste-ready, duplicate detection by name and size

    <span class="fc-select__option-check" aria-hidden="true">&#10003;</span>
    <span class="fc-select__option-label">Claude Opus 5</span>
  </div>
  <!-- Unavailable, not hidden: the user can see it exists and why not. -->
  <div class="fc-select__option" role="option" aria-disabled="true">
    <span class="fc-select__option-label">Llama 4 (needs 64 GB)</span>
  </div>
</div>
    js 
    import { FutureCssSelect } from "future-css/select";

const select = new FutureCssSelect({
  invoker: "#model-select",
  list:    "#model-list",

  // Fires only on a real commit. Escape deliberately does NOT fire it:
  // a consumer would persist a value the user declined to choose.
  onChange: (value, option) => {
    console.log(value, option.label);
  },
});

// Substring search, which a prefix typeahead cannot do.
select.filter("sonnet");

// Optional: run the model in Rust. Returns false -- and keeps the JS model --
// whenever the module is absent or fails to load, so the call needs no guard.
await select.useWasm("/dist/wasm/fc-select/web/fc_select.js");

// Keyboard contract, all in the binding:
  //   Enter / Space   open, or commit the highlighted option
  //   ArrowUp / Down  move, wrapping, stepping over unavailable options
  //   Home / End      first / last selectable
  //   typeahead       prefix match, 600 ms window
  //   Escape          close AND restore the committed value
  //   Tab             commit and leave -- never trapped
  //
  // DOM focus stays on the invoker throughout. The highlight is conveyed with
  // aria-activedescendant, which is what keeps the control reachable by Tab.

    Diff

    Added and removed lines differ by background, by foreground, by a sign glyph, and by data-fc-diff. Drop any one of those — a colour-blind reader, a printer, forced colours — and the distinction survives. Lines present on only one side show no number on the other, rather than inventing one.

    js 
    import { diffLines, diffStats } from "future-css/diff";

const lines = diffLines(before, after);   // Myers, O(N*D)
const { added, removed } = diffStats(lines);

for (const line of lines) {
  const row = document.createElement("div");
  row.className = "fc-diff__line";

  // Machine-readable state. CSS, tests, and agents all read this one attribute.
  if (line.kind !== "equal") row.dataset.fcDiff = line.kind;

  // Human-readable state. Text, not a CSS content value, so it survives
  // forced colors and can be selected. Hidden: the attribute already says it.
  const sign = document.createElement("span");
  sign.className = "fc-diff__marker";
  sign.setAttribute("aria-hidden", "true");
  sign.textContent = line.kind === "add" ? "+"
                   : line.kind === "remove" ? "\u2212" : " ";

  // null means "not on this side" -- render empty rather than 0.
  const oldNo = document.createElement("span");
  oldNo.className = "fc-diff__num";
  oldNo.setAttribute("aria-hidden", "true");
  oldNo.textContent = line.oldLine ?? "";

  row.append(sign, oldNo, content);
  body.append(row);
}

    Design tokens

    Colours are named by purpose, never by hue, so a theme can remap them. Each pairing below is read from the live stylesheet, so the ratio shown is the one actually rendering — computed, not estimated.

    css 
    /* Components reference SEMANTIC tokens only. A primitive is an
   implementation detail a theme may remap -- referencing one directly
   means the theme cannot change it. */
.my-panel {
  background-color: var(--fc-color-bg-surface);
  color:            var(--fc-color-text-default);
  border:           var(--fc-border-width-thin) solid var(--fc-color-border-subtle);
}

/* Theming is one attribute. Every themed token is a light-dark() pair, so
   this re-themes all 90 of them with no component-level rule anywhere. */
[data-fc-theme="dark"] { color-scheme: dark; }

/* Direction is structural, not a parallel stylesheet: logical properties
   mean RTL needs no mirrored rules at all. */
.my-panel { margin-inline-start: var(--fc-space-4); }
